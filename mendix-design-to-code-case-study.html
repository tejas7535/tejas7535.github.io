Decoupling brand from a low-code build.

A design-token pipeline that pulls Schaeffler's brand variables straight out of Figma and into Mendix's Atlas UI — so a color or spacing change ships without a developer ever opening a stylesheet.

01 — Context

Every brand tweak meant a developer, a stylesheet, and a wait.

Mendix's Atlas UI is fast to build with, but its styling lives inside the app: hex codes and spacing values are typed by hand into SCSS files. When Schaeffler's brand guidelines shifted, that change had to be manually re-typed into every low-code app, by a developer, one variable at a time.

02 — Objectives

Three constraints shaped the whole build.

The pipeline had to move the source of truth for branding, remove manual CSS work, and do it without touching Atlas's native components — anything else risked breaking every app built on top of it.

Decouple style

Move the source of truth for branding out of Mendix entirely, into an external, design-controlled data layer that designers — not developers — own.

Eliminate manual CSS

Automate styling updates end to end, so a brand-guideline change rewrites the theme file instantly, with zero hand-typed hex codes.

Protect the architecture

Introduce a zero-maintenance workflow that leverages styling updates without ever modifying native Atlas UI components.

03 — Team

Three roles, one hand-off point.

The design shrinks the hand-off between design and engineering down to a single artifact: a token file. Everyone downstream reads from it instead of from each other.

05 — Roadmap

Four stages, start to validated.

Each stage had a single owner and a single exit criterion, so the POC could be checked off in order rather than debugged as one big black box.

Extract, then structure

Pulled every existing Mendix branding value out of the Atlas theme and modeled them as clean, hierarchical JSON — the raw material the rest of the pipeline runs on.

Teach Style Dictionary the Atlas shape

Set up Style Dictionary to parse that JSON and output SCSS variables that already match Atlas UI's expected structure — no renaming or reformatting needed on the Mendix side.

Wire it into the theme, once

Brought the generated _brand-variables.scss asset into the Mendix project and linked it to the custom theme. This is the one manual step in the whole flow.

Prove it end to end

Changed a value in the JSON, let the GitHub Action run unattended, then opened the running Mendix app to confirm the new brand value appeared with no code touched.

07 — Definition of done

What "successful" had to mean.

The POC only counted as complete when a non-developer could change a value in the design repo and see it live in Mendix, with no code touched.

Zero hardcoded styles

No arbitrary hex codes or pixel values left in the Mendix _custom-variables.scss file — everything traces back to a token.

Automated asset hand-off

A git push in the design repo automatically opens or updates a pull request in the Mendix app repository — no one has to remember to do it.

Clean theme compilation

Mendix Studio Pro processes the automated stylesheet update and reflects the brand change correctly during local runtime testing.

08 — Reflection

What this proved — and what's still open.

“The real win wasn't the automation — it was making the designer's Figma file the actual source of truth, instead of a reference someone re-typed later.”
— Tejas Shewale, on the design intent behind the pipeline
  • Hover-state colors derived from SCSS runtime functions (darken(), mix()) are currently approximated and need verifying against a live Mendix instance.
  • The Mendix-mapping step is still a one-time manual wiring — by design, to avoid touching native Atlas components automatically.
  • Next step is extending the same token structure across typography and spacing primitives, not just color.
